# APPOINTMEN-52 — Twilio WhatsApp Sandbox Go/No-Go Spike (Manual Runbook)

**Status:** Not executed. This is a runbook for a human to run manually — it requires a real
Twilio account, a real WhatsApp-enabled phone, and a publicly reachable webhook URL, none of
which an agent session can provide on its own. No code change accompanies this document.

## Why this exists

APPOINTMEN-52's AC calls for an actual live round-trip through Twilio's WhatsApp Sandbox
(inbound message → backend webhook → outbound reply) and a go/no-go answer on whether Sandbox
can reliably render interactive/quick-reply buttons — before Stories 7.1–7.4 were built. In
practice, 7.1–7.4 (APPOINTMEN-48, -49, -50, -51) already shipped without this spike having run,
so at this point the spike serves as **retroactive verification** of what was already assumed
(the plain-text-only design), not as a design-input gate. Run it to confirm the assumption
holds, or to surface an integration problem before demo/UAT.

## What already exists in the codebase

- `B2B_BE/app/api/webhooks/whatsapp.py` — the Twilio WhatsApp webhook adapter (built by
  APPOINTMEN-48/49/50/51). It expects a Twilio-format `POST` with `From`/`Body` form fields,
  strips the `whatsapp:` prefix, and replies with TwiML built from the same
  `booking_agent.handle_message` / `manager_agent.*` functions Web Chat uses.
- No Twilio credentials exist anywhere in this repo (checked `B2B_BE/.env.example`,
  `app/config.py`, and a full-repo grep for `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` — none
  found). The webhook adapter only *receives* Twilio's POST and returns TwiML in the HTTP
  response — it does not need outbound API credentials to reply, only to send an
  out-of-band/proactive message, which nothing in this codebase does yet.
- Twilio webhook signature verification is explicitly out of scope on every WhatsApp ticket so
  far (APPOINTMEN-48/49/50) — the spike does not need to set this up either, but note it as a
  known gap if this ever goes past a sandbox demo.

## Prerequisites (human-only steps)

1. A Twilio account (trial is sufficient) with the WhatsApp Sandbox enabled — Twilio Console →
   Messaging → Try it out → Send a WhatsApp message.
2. A phone with WhatsApp, joined to the Sandbox by sending the Sandbox's `join <code>` message
   to the Sandbox's WhatsApp number.
3. The backend running somewhere Twilio can reach over the public internet:
   - Local dev: run the backend (`docker compose up` per `B2B_BE`'s existing local-orchestration
     setup from APPOINTMEN-11) and expose it with a tunnel (e.g. `ngrok http <port>`), or
   - A deployed environment, if one exists, reachable at a stable HTTPS URL.
4. In the Twilio Console's WhatsApp Sandbox settings, set "WHEN A MESSAGE COMES IN" to
   `https://<public-url>/webhooks/whatsapp` (confirm the exact route in `whatsapp.py` — it may
   be mounted under a prefix; check `app/main.py`'s router registration).

## Steps

1. From the WhatsApp-joined phone, send a plain message that should resolve to a known Customer,
   Staff, or Owner/Admin phone number already seeded in the dev database (see APPOINTMEN-9/13/17
   seed data) — e.g. Meena's or Ramesh's number, or a fresh number to exercise the
   customer-identity path from APPOINTMEN-48.
2. **Reachability check:** confirm the message reaches the backend — watch the backend's logs
   (or add a temporary log line) for the inbound `POST /webhooks/whatsapp` call. Record pass/fail.
3. **Round-trip check:** confirm the reply generated by `handle_message` / the Manager Agent
   dispatch is actually delivered back to the phone as a WhatsApp message via Twilio's TwiML
   response mechanism. Record pass/fail.
4. **Interactive-button go/no-go:** in the Twilio Console, attempt to send (or configure) a
   WhatsApp message using Twilio's Content API with Quick Reply buttons to the Sandbox number,
   or consult Twilio's current documentation on Sandbox limitations for rich/interactive content
   templates (historically, Sandbox — as opposed to an approved WhatsApp Business number — has
   not supported approved Content API templates required for quick-reply buttons; this must be
   confirmed against Twilio's current docs/console at spike time, not assumed from this note).
   Record the answer as **go** or **no-go**, with the evidence (screenshot, console message, or
   doc link) that justifies it.
5. If the answer is **no-go** (buttons unsupported in Sandbox): this confirms the plain-text-only
   design already shipped in APPOINTMEN-50/51 is correct and final, per the ticket's own AC — no
   further code change is implied. If the answer is **go**: flag to the team, since it would mean
   APPOINTMEN-50/51's plain-text-only scoping decision should be revisited for a future ticket
   (not retroactively — those tickets are already merged and in Ready for UAT).
